# 多模态量化踩坑复盘：从 bf16 掉点说起

一年前做过一次失败的尝试：把一个 Qwen-VL 模型全模型转 bf16 推理，目标是省显存让单卡跑得起来，结果**召回率和准确率双双下降约 10%**。当时没时间深究，只记了一句"bf16 在这个场景不行"。

最近回头把这笔账算清楚，才发现当时犯的错和学到的东西都比想象中多。这篇记录一次复盘，也记录一次关于"精度"这件事的重新认识。

## 1. 先搞清楚一个概念：bf16 不是量化

这是最根源的错误 —— 当时的认知是"只要不是 fp32 全精度推理，就都算量化"。于是把"转 bf16"当成了"做量化"，后面所有的归因都从这个错误前提出发。

实际上降精度的手段分成两个完全不同的类别：

| 操作 | 类别 | 本质 |
|---|---|---|
| fp32 → bf16 / fp16 | **半精度推理** | 还是浮点数，只是位数更少 |
| fp32 → fp8 | 介于两者之间 | 通常也归到量化 |
| fp32 → int8 / int4 | **真正的量化** | 浮点变定点，需要 scale / zero-point |

两者的**误差模型完全不同**：
- 半精度推理的误差来自**尾数截断**，是连续分布的微小舍入
- 量化的误差来自**离散化**，需要标定和缩放，误差分布和 outlier 强相关

把两件事混为一谈，方向就会从一开始就是歪的。

### bf16 和 fp16 的位结构对比

bf16 和 fp16 虽然都是 16 位浮点，但内部结构截然不同：

![bf16 vs fp16 位结构对比](/images/bf16_vs_fp16_bits.png)

```
fp32:  1 符号位 +  8 指数位 + 23 尾数位
bf16:  1 符号位 +  8 指数位 +  7 尾数位   ← 范围大，精度差
fp16:  1 符号位 +  5 指数位 + 10 尾数位   ← 范围小，精度好
```

一个直接推论：

- **bf16 的相对精度 ≈ $2^{-7} ≈ 0.78\%$**
- **fp16 的相对精度 ≈ $2^{-10} ≈ 0.098\%$**

bf16 比 fp16 精度差了将近一个数量级，代价是换来了更大的动态范围（和 fp32 的指数位一致，不容易溢出）。

### 训练选 bf16 ≠ 推理也要选 bf16

训练阶段选 bf16 是社区共识：梯度和激活可能出现大范围的数值跨度，指数位多能防溢出，保训练稳定。

但推理阶段的诉求不一样 —— 前向过程里数值范围其实相对可控，真正会暴露精度缺陷的是**小激活的尾数截断**。换句话说：

> **训练选 bf16 是铁律，推理选 bf16 不是。**

这是当时我根本没想过的问题。

## 2. 那 10% 到底是怎么没的

事后复盘，这 10% 不是单一原因造成的，而是**任务特性 + 精度损伤 + 框架黑箱**三重叠加的结果。

### 第一重：任务本身是地狱难度

任务属于**高精度要求的视觉理解场景**，具体包含：
- 细粒度分类（不是"车"，是"白色 SUV"、"载货卡车"这一层）
- 小目标检测（远处只有几十个像素的目标）
- 空间关系推理
- 场景内的文字识别（OCR 任务嵌在 VQA 里）

这类任务对视觉特征精度的要求，比通用 caption / VQA 高出 **3–5 倍**。通用 benchmark 上看起来微不足道的掉点，在这类任务上会被放大成肉眼可见的质量塌陷。

### 第二重：bf16 杀死了小激活

ViT 内部有一个关键事实：某些 head 的激活集中在 **$10^{-3}$ 量级**，对应的往往是**小目标的特征和细节纹理**。

- bf16 的相对误差是 0.78%
- 对大激活（$1 \sim 10$ 量级）几乎无感
- 对小激活（$10^{-3}$ 量级）**直接归零**

结果就是：大目标还能认，小目标（远处的细节对象、小尺寸文字）**直接从特征图上消失**。召回率断崖式下降的来源就在这里。

还有一个隐藏信息：很多开源视觉塔（CLIP ViT、EVA-CLIP 等）原始权重是 **fp16 训练**的，强转 bf16 等于换到了一个不匹配的表示空间 —— 尾数精度还降了。

### 第三重：推理框架藏着一堆隐式操作

"效率优先"的推理框架（vLLM / lmdeploy 这类）在你改 `dtype=bf16` 时，背后可能顺手做了一堆事：

| 操作 | 你以为 | 实际可能发生 |
|---|---|---|
| `dtype=bf16` | 只改 LLM | ✅ 包括视觉塔 |
| KV cache | 没动 | 可能默认开了 fp8 / int8 |
| 视觉 token 上限 | 没动 | 可能被砍（省显存副作用） |
| 图像预处理 | 对齐 | 可能有隐式 cast |
| decoding 参数 | 一致 | 框架间默认值不同 |

**一个按钮，背后是一堆变量同时变化**。这时候任何"把掉点归因给 bf16"的结论，从方法论上都站不住脚。

### 综合归因

![10% 掉点的归因分解](/images/quant_attribution_pie.png)

最终我对这 10% 掉点的归因判断（基于事后分析，不是严格实验结论）：

```
40%  bf16 对 ViT 小激活的精度损伤（+ 视觉塔本是 fp16 训练）
25%  框架砍了视觉 token 上限
15%  图像预处理 / 归一化 dtype 不对齐
10%  decoding 参数差异
10%  评测随机性 + 其他
```

> **本质错误不是"bf16 不行"，而是"同时改了多个变量却只归因给一个"。**
> 这不是量化问题，是实验方法论问题。

## 3. 多模态量化的若干铁律

跳出这次具体踩坑，做多模态推理加速/量化迟早会遇到这些坑。把它们整理成一组可复用的判断规则。

### 铁律 1：视觉塔不能一视同仁

- ViT 的激活有大量 outlier channel，个别通道可以达到均值的 100 倍
- per-tensor scale 一罩下去，非 outlier 的精度全毁
- 更糟的是**视觉塔在整个 VLM 里占比通常只有 10%–20%**，量化它的收益本身就很小

**做法**：视觉塔保 bf16 / fp16，只量化 LLM 部分。收益最大、代价最小。

### 铁律 2：Projector 是隐藏的精度杀手

Projector 模块参数量很小（几十 M 到几百 M），容易被忽视，但它是**跨模态对齐的唯一信息瓶颈**。任何在 projector 上的量化误差，都会被后面的 LLM 逐层放大。

**做法**：**不要量化 projector**。参数量小，不量化几乎不影响整体显存收益。

### 铁律 3：校准集必须包含图文混合样本

activation 量化依赖 calibration 集来统计分布、确定 scale。如果校准集只用文本：

- 图像 token 进到 LLM 时会遇到它没见过的数值分布
- 要么溢出（超出 scale 的 clamp 范围），要么塌陷（都在 0 附近）

**做法**：calibration 集必须**图文混合**，且图像要覆盖目标下游分布。

### 铁律 4：KV cache 在长图像序列下会累积崩溃

一张 448×448 图 → 256+ visual tokens，高清模式 → 1000+。图像 token 的 K/V 方差远大于文本，共用一套 scale 会让文本 token 的精度被图像拖垮。

**做法**：**分开 scale**，或只量化文本部分的 KV cache。

### 铁律 5：动态分辨率模型更难量化

Qwen2-VL、InternVL 这类支持动态分辨率的模型，每张图的 token 数和分布都不一样，**静态量化的 calibration 直接失效**。

**做法**：要么用动态量化，要么 calibration 时覆盖各种分辨率。

### 铁律 6：评估必须包含幻觉率

视觉特征被量化模糊后，会发生一个隐蔽现象：**LLM 更依赖语言先验来填空** —— 看不清就编。通用 benchmark 的准确率未必明显下降，但幻觉率会显著上升。

**做法**：必须单独评估幻觉率。POPE benchmark 或人工抽检"图里不存在的物体是否被提及"。

### 铁律 7：QK 和 softmax 永远保持高精度

ViT 的 attention 对量化极度敏感。QK matmul 或 softmax 的量化误差会让 attention 分布**塌陷为极端形态**（过度尖锐或过度平坦），多目标场景立刻废掉。

**做法**：**QK 和 softmax 始终保持 bf16 / fp32**，不参与量化。

### 铁律 8：细粒度任务是量化的试金石

| 任务类型 | 对精度的容忍度 |
|---|---|
| VQA、captioning | 宽容 |
| OCR、图表理解、GUI agent、细粒度识别 | 严苛 |

**评测必须按下游任务做**，不能只看通用 benchmark。通用 benchmark 的"能用"在细粒度任务上可能是"完全不能用"。

## 4. 如果重来一次

给未来自己留一份 checklist，下次再做推理加速时照着走：

1. **先做单变量实验**：只改 dtype，其他一切（框架、KV cache、token 数、预处理）全部冻结，先隔离框架切换本身的影响
2. **bf16 掉了就试 fp16**：如果 bf16 掉点，立刻换 fp16 再测一遍 —— 这是隔离"尾数精度"最便宜的验证
3. **视觉塔保高精度**：只对 LLM 部分降精度，视觉塔和 projector 保 bf16 / fp16
4. **按下游任务评测**：不看通用 benchmark，只看目标场景下的细粒度指标（尤其是小目标召回和幻觉率）
5. **如果省不下显存**：承认这个业务场景不适合当前的量化方案，回去和团队聊真实的"显存 vs 精度"取舍，而不是硬上

## 5. 一些个人反思

写到这里，技术的东西讲得差不多了。最后说一点这次复盘自己的反思：

**第一，概念混淆比技术缺陷更致命**。我当时以为自己在做"量化"，其实做的是"半精度推理"，复盘方向从一开始就是错的。这种错误靠经验补不回来，只能靠概念的精确性。

**第二，别把同事搭的框架当黑箱**。一个"dtype=bf16"的开关背后同时动了多个变量 —— 在这种环境下谈归因是自欺欺人。下次一定先把变量剥开。

**第三，训练的最优解不等于推理的最优解**。bf16 在训练里是共识，但推理的诉求完全不同，尾数精度才是这里的瓶颈。**场景变了，最优解就变了** —— 这个提醒对任何技术决策都成立。

**第四，犯错不丢人，犯错还能过一年再回来把账算清楚，这本身就是积累。** 真正掉队的不是犯过错的人，是犯完错就彻底忘记的人。

## 结语

多模态量化不是一件"把 LLM 量化流程直接搬过来"的事。视觉塔和语言塔的误差容忍度、激活分布、权重来源全都不一样；推理框架的每一个"智能默认值"都是一个潜在的隐式变量；下游任务的精度要求也千差万别。

在有明确业务约束的场景下谈量化，第一件事不是选算法，是**先把变量剥开、把任务特性讲清楚、把评测做对**。剩下的才是算法层的取舍。
